Summary

Ran a 4-layer read-only integrity audit across the full 9-filing corpus (AAPL, MSFT, TSLA × 2023/2024/2025), covering both the SQLite nodes table and the persisted storage/summary_index/ TreeIndex artifacts. Three of four layers came back fully clean: all 45 storage JSON files parse without truncation, every filing's TreeIndex tree structure is internally consistent (no orphan node references, no docstore nodes excluded from the tree), and the nodes table has zero empty-content rows, zero duplicate node_ids, and exactly the 9 expected filings. The fourth layer — Markdown table integrity in the LlamaParse output (data/parsed/*.md) — found a real, reproducible defect: 31 tables across 5 of 9 filings have a misaligned header caused by a units caption ("(in millions)"/"(in thousands)") merging into the table's first cell. This is a source-parsing quality issue, not corruption of the ingested nodes or the built index — the affected tables are all in AAPL-adjacent balance-sheet/cash-flow style statements in MSFT and TSLA.

What Was Checked

  1. Storage file validity — every one of 9 filings × 5 files (docstore.json, index_store.json, graph_store.json, default__vector_store.json, image__vector_store.json) parsed as complete, non-truncated JSON.
  2. Tree structure consistency — for each filing, every node ID referenced by the TreeIndex's all_nodes/root_nodes/node_id_to_children_ids structures was cross-checked against the actual node IDs present in docstore.json. No orphan references (tree pointing at a node that doesn't exist), no uncovered nodes (docstore entries the tree never references).
  3. Markdown table integrity — scanned data/parsed/*.md (the direct LlamaParse output, which is where the ingestion prompt's "never split or truncate a table" guarantee actually applies) for tables missing a header separator row or with inconsistent column counts across rows. Deliberately not checked at the TreeIndex node-chunk level — chunk boundaries cutting through a table there is expected/benign, not a corruption signal, since chunking happens after parsing.
  4. DB sanity — nodes table checked for NULL/empty content, duplicate node_id values, and that document_id coverage is exactly the 9 expected filings (no missing, no unexpected extras).

Finding: Misaligned Table Headers in 5 Filings

In data/parsed/MSFT_2023.md, MSFT_2024.md, MSFT_2025.md, TSLA_2023.md, and TSLA_2025.md, 31 tables total show the same defect. Example from MSFT_2023.md line 1580:

(In millions)|                    |          |         |
| ------------------ | -------- | --------- | -------- |
| 2024                | Thereafter | Total   |          |
| Long-term debt: (a) | Principal payments | $ 5,250 | $ 47,616 |

The caption (In millions) has no leading |, so it merges into what should be a separate title line above the table. The separator row (| --- | --- |...) is then misidentified as the table's first data row, and the real header row ("2024 | Thereafter | Total") ends up one row too late. Column counts are also ragged — 5 pipe-delimited columns in the separator vs. 3-4 populated cells in most data rows. Confirmed the identical pattern in TSLA_2023.md line 1552 (a Consolidated Statements of Comprehensive Income table). AAPL_2023/2024/2025.md and TSLA_2024.md have zero flagged tables — clean.

This is a LlamaParse extraction artifact specific to tables immediately preceded by a units caption line, not a database or index corruption. It affects the source Markdown, and by extension whatever nodes were chunked from those specific table regions — but nothing was silently dropped; the data is present, just header-misaligned.

Risks

  • The 31 misaligned tables sit inside nodes that P1 (vector) and P2 (BM25) will retrieve and P3 (structural) has already indexed. A retrieval hit on one of these specific nodes will hand the LLM a slightly garbled table (right numbers, wrong header alignment) rather than a cleanly labeled one — worth keeping in mind if a judge/critic ever flags an answer as "numerically right but mislabeled" for a contractual-obligations or comprehensive-income query against MSFT or TSLA.
  • Root cause is upstream in LlamaParse's handling of caption-prefixed tables, not in this project's own parsing/chunking code — no local bug to fix, only a data-quality caveat to carry forward.
