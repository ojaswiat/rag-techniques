Act 0 · Prologue

A reflex on trial

Vector search is the default answer to almost every retrieval question. This study asked whether that reflex is earned.

Ask a room of engineers how to search a document. Most will say embeddings.

Dense vector retrieval has become the reflex answer. It is what the tutorials teach and what the vendors sell.

But a 1994 statistical ranking function called BM25 still sits in every search engine built. It has no model, no training and no embedding.

And a third idea exists. Build a summary tree over the document, then walk down it. Structure instead of similarity.

This study put all three on the same 900 questions and measured what happened.

Three retrieval paradigms. One corpus. One answering model. One judge. Nine hundred scored cells, and no place to hide.

1. The reflex is not earned, but it is not wrong either. Semantic and statistical retrieval are statistically indistinguishable here. The paired difference is -0.160, interval [-0.340, +0.013]. It spans zero.

2. The average hides a real split. BM25 wins the implicit-text quadrant outright. The vector pipeline leads on implicit tables. Pooled, they cancel.

3. Structure lost, and lost expensively. The summary tree trails by about two judge points. It also took 10.6 hours and 2.5 million tokens to build.

A 32-year-old algorithm with no model matched a modern embedding stack. It also built its index in under one second.

The rest of this document is how that result was produced. It covers what nearly broke it, and what it lets you claim.

Act I · The Design

Building a fair fight

A comparison is only worth running if the thing being compared is the only thing allowed to vary. Most of the design is about holding everything else still.

The research question is narrow on purpose.

Does the way a retriever is built change how well a language model answers questions about an annual report?

To answer it, three paradigms index the identical corpus. They answer the identical questions through the identical model. They are graded by the identical judge.

Anything that differs between them is the paradigm. Nothing else is permitted to move.

The three contenders

P1 Vector

Matches on meaning.

Dense embeddings in ChromaDB, reranked by a local cross-encoder.

P2 BM25

Matches on terms and their rarity.

rank_bm25 over the same nodes. No model of any kind.

P3 Structural

Matches on position in a hierarchy.

A LlamaIndex summary tree per filing, traversed by embedding.

What is held constant

  1. The corpus. All three index the same 18,297 nodes from the same 13 filings.
  2. The questions. All three answer the same 100 questions at three depths. That gives 900 cells.
  3. The answering model. One model writes every answer. Differences trace back to retrieval alone.
  4. The grader. One judge, one rubric, with a fingerprint stored per row.
  5. What a pipeline never sees. Only the question and its own retrieved nodes. No ground truth, no hints, no metadata filter.

How one question becomes one scored row

The only thing that changes between the three runs is the retriever. Everything downstream is held identical.

The system that does it

Nine layers, twenty-nine source modules. Each layer only talks to its neighbours.

Nine layers. These are the modules on the main path, not every file in the repository. Arrows show the direction data moves, not the order the code was written.

Where everything is kept

Five SQLite tables. The three question tables are disjoint by construction.

One results row exists per question, pipeline and depth. The three question tables are disjoint by construction: no query_id appears in more than one, so the judge is never calibrated on a row used to test it.

What gets measured

Three pillars, because a paradigm can win one and lose another.

A paradigm can win one pillar and lose another. Reporting all three is what stops a single favourable metric standing in for the result.

  • The answerer that writes an answer is never the judge that scores it.

Every call runs at temperature zero. The answerer and judge are each pinned to one upstream host.

That pinning matters. OpenRouter otherwise load-balances across backends with different quantisation. Two calls could land on numerically different models.

Act II · The Build

Ten weeks, eight phases, 270 commits

The schedule was written before any code existed. It held, but not in the shape it was drawn.

The budget was a solo ten-week build, with the tail reserved for writing.

Two constraints shaped everything. The project had to cost nothing, and it had to survive being interrupted.

Free tiers are rate-limited, so long jobs get throttled. Throttled jobs get killed. Killed jobs must resume without re-spending quota.

That single requirement is why the database has a uniqueness constraint on every benchmark cell.

Phases overlap deliberately. The 900-cell run was designed to start the moment the judge gate passed, and to keep running in the background while analysis was written.

The phases, told quickly

  • Week 1

    Phase 1 · The rails

    Five SQLite tables, three provider clients, one factory. Retry with backoff, a semaphore capped at five workers, and a throttle flag on every loop.

    Nothing here calls a model in anger. It builds the things that keep the project at zero cost and crash-resilient.

  • Weeks 1 to 3

    Phase 2 · Turning filings into nodes

    Thirteen 10-K filings pulled from SEC EDGAR. Parsed by LlamaParse in atomic-table mode, so no table is ever bisected.

    Result: 18,297 nodes, each with a stable id. Every downstream metric keys off that id, so correctness here is load-bearing.

  • Weeks 3 to 4

    Phase 3 · The expensive index

    The only index allowed to call a model. One summary tree per filing, built once and cached forever.

    It took 10.6 hours and roughly 2.5 million tokens. It became the longest phase in the project by wall clock.

  • Weeks 4 to 6

    Phase 4 · Making the questions

    A generator proposes a question, an answer and its evidence. A critic from a different family tries to verify it, blind.

    The critic gets a search tool over the whole filing. It never sees the proposed answer. A deterministic code check compares what both found.

  • Weeks 5 to 7

    Phase 5 · Three retrievers, one interface

    All three implement the same abstract class. That is what makes the swap clean, and the comparison fair.

    P2 was held to pure statistics deliberately. LlamaIndex offers a keyword index that calls an LLM, which would have destroyed the contrast.

  • Weeks 6 to 8

    Phase 6 · The gate

    A hard stop. No full run was permitted until the judge proved itself on sixty held-out outputs.

  • Weeks 7 to 10

    Phase 7 · The run

    Nine hundred cells, once each, at temperature zero. Resumable after every committed row.

  • Weeks 8 to 12

    Phase 8 · Making sense of it

    Aggregation, bootstrap intervals, figures, index build cost, and the reports you are reading.

Act III · The Trials

Fifteen bugs, thirty-eight deviations

Nothing in this project went to plan. That is not a confession, it is the methodology chapter. Every departure is logged with what was proposed, what changed, and why.

Research code fails in a specific way. It does not crash. It produces a number.

The number looks plausible. It goes into a table. Nobody checks it again.

Four of the fifteen bugs below were exactly that shape. Each would have invalidated the comparison while leaving every test green.

These fifteen are not every bug. The defect log records only major or load-bearing failures, not the routine nits caught in review.

Ordinary fixes went to the operations log instead. What follows is the subset that changed a decision, a metric, or the design.

The four that would have sunk the study

Chroma ate the corpus

Duplicate node ids made Chroma silently drop real filing data. No error, no warning. The vector index would have been quietly incomplete.

Chroma renamed our field

A reserved metadata key overwrote document_id. P1's per-document retrieval isolation would have broken without anything failing.

P1 was reading cheat notes

Structural metadata leaked into the text P1 embedded and reranked. One pipeline was seeing section headers the others were not.

The dataset was two companies short

The generator only ever saw 9 of 13 filings. The benchmark would have shipped missing two companies entirely.

None of these threw an exception. All four were caught by a test written after someone asked a suspicious question.

Thirty-eight deviations from the original design

A deviation is not a mistake. It is a documented departure from what the specification said, with a reason.

Thirty-eight departures from the original design, every one logged with what was proposed, what changed, and why.

The largest group is provider or model changes. Ten of thirty-eight.

These thirty-eight are the departures worth recording. Small refinements made during normal implementation are not among them.

That is what a zero-cost constraint does to a project. Free tiers move, models get retired, and limits bite.

The provider exodus

Three migrations in eight weeks, each forced by a different wall.

Deviations 7, 23, 24 and 29. Each move was forced by a hard limit, not a preference, and each is logged with the wall that caused it.

  1. Groq could not sustain the P3 build. Its free tier is token-bound. Daily limits were exhausted mid-build, repeatedly.
  2. NVIDIA NIM gave headroom, then throttled too. It is request-bound rather than token-bound, which suited a bulk job. Its own limits still bit.
  3. OpenRouter took the generator, then everything. A structural tokens-per- minute wall on NIM made generation impossible at volume.
  4. Finally, a paid tier for the run itself. The 900-cell matrix on Groq's free tier needed two to three weeks of supervised, interrupted running.

That last move cost about $1.55 and completed the matrix in roughly ninety-five minutes.

Two real costs exist. A one-time $10 account top-up, taken to lift a daily request cap, and roughly $1 to $1.55 for the run.

Everything else ran on free tiers or local hardware. Both charges are one-off, so the ban on per-hour infrastructure held throughout.

Two challenges that were absorbed, not solved

NIM still throttles P3

Even after the move, the summary build hits rate limits on long runs. Retry, backoff and 40 requests per minute absorb it. Builds just take longer.

Per-filing resumability saved it

Each filing writes to a temp directory, then renames atomically. A throttled eleven-hour build is safe to interrupt and restart.

Act IV · The Instrument

Proving the ruler before measuring

A benchmark graded by a language model is only as good as that model. So the judge had to pass a hard gate before it touched a single benchmark cell.

Nine hundred answers cannot be marked by hand. A model has to do it.

That creates an obvious problem. If the judge is unreliable, every number in this document is noise.

The design answer was a gate. No full run was permitted until the judge proved itself on held-out data.

The rubric

Five bands. The judge scores content only, against the ground-truth answer.

5

Fully correct

Matches the ground truth, complete and precise.

4

Right value, short of complete

Correct value, falling short on framing.

3

Half an answer

One half of a two-part answer, other half absent.

2

Right area, wrong figure

Reaches the right part, reports the wrong value.

1

Wrong

Unsupported, fabricated, or a refusal to answer.

Citation validity is deliberately absent from that list.

It is checked in code instead. Asking the judge as well would let a model's guess override a deterministic check.

The scale was collapsed mid-project, from 1 to 10 down to 1 to 5. Ten bands asked for distinctions the rubric could not define. The judge could not apply them consistently.

That collapse created its own hazard. Fifteen gate rows kept scores written under the retired rubric. Seven held values between 1 and 5, indistinguishable from valid new scores.

A resume keyed on "has a score" would have silently mixed two rubrics. Nothing would have failed. Nothing would have looked wrong.

The fix: fingerprint every score

Each judged row stores a digest of the grading model plus the exact system prompt.

That prompt embeds the rubric text and the quadrant's five calibration exemplars. Change any of them and the fingerprint changes.

Resume now skips a row only if it has a score and its fingerprint matches the rubric currently in force.

All 900 benchmark rows carry a fingerprint. There are exactly four distinct values, 225 rows each, one per quadrant.

Recomputing from the current rubric reproduces the stored value in all four. That is what rules out silent rubric drift mid-run.

Act V · The Run

Nine hundred cells, and one near-disaster

The matrix ran in a single pass. Then a routine check found that the ruler itself was wrong.

The benchmark executed cleanly. Nine hundred cells, one pass, ninety-five minutes.

Then a check on the recall metric produced something impossible. One question had a maximum achievable recall of 0.012.

It asked for a single figure. Its answer key cited 423 nodes.

The ruler was broken

Only 60 of the 423 squares are drawn. Drawing all of them would not fit the figure, which is rather the point.

The generator was told to cite evidence from the section it was shown. It was never told the list had to be minimal.

On twenty of one hundred questions it simply returned the whole section.

  • Recall divides by the size of the gold set, with no cap.
  • A gold set larger than the deepest retrieval setting makes full recall unreachable.
  • Twenty-four rows carried a ceiling below 1.0. The mean ceiling was 0.869.
  • Precision breaks the other way: almost any in-section node counts as a hit.

This is the moment the study nearly failed quietly. The obvious remedy was to leave the data alone and report a different metric.

That fails on inspection. Capped recall would score a pipeline retrieving any five nodes from a 423-node section at a perfect 1.000.

Worse, the defect was not common-mode. Repairing it inverted the vector against BM25 ranking on precision. A defect that can reorder two of three pipelines cannot be disclosed and left in place.

How it was repaired without touching the result

  1. The retention rule is mechanical and applied uniformly.
  2. It is blind to every pipeline's output. No retrieval result was consulted.
  3. A node is kept only if it demonstrably contains or produces the answer.
  4. The applier refuses to write if any row fails to verify. It fired once.
  5. Replaying it against the pre-repair backup reproduces the database exactly.

Twenty-four rows fell from 1,412 citations to 34. The mean recall ceiling is now 1.000.

Act VI · The Verdict

What this licenses you to claim

A result is only as strong as the limitations stated beside it. Every one an examiner could raise is here, with the argument to make.

material

Latency does not separate the three paradigms

What the data shows. Median per-cell latency differs by under a fifth of a second across all three. The means differ more, but they are pulled by rare slow calls to a shared hosted provider.

How to defend it. Report query latency as a null result, and say why. Every cell routes through the same answering model, so the shared call dominates. Rest the efficiency claim on index build cost and tokens per query, which are measured cleanly.

material

Some answers were correct without any evidence retrieved

What the data shows. Nineteen of 900 cells scored 4 or 5 having retrieved no ground-truth node. Sixteen belong to the structural pipeline. Those answers came from the model's own knowledge of these companies.

How to defend it. Disclose it as a floor on parametric leakage, and give the direction. It inflates the weakest pipeline, because a retriever that returns nothing useful leaves the model free to recall. The measured gap is therefore a lower bound.

material

One run per cell, so run-to-run variance is unmeasured

What the data shows. Every cell executed once at temperature zero, with each model pinned to a single upstream host so quantisation could not vary. The intervals describe variation across questions.

How to defend it. State that the intervals are question-level, not run-level. The design trades repeated sampling for breadth: 900 distinct cells rather than a smaller matrix sampled repeatedly. Temperature zero and host pinning are what make one run defensible. Cite both.

material

The gate measures concordance, not human agreement

What the data shows. The judge was compared against an independent second scoring of the same sixty outputs, produced under blinding. It is not an external human annotator.

How to defend it. Call it cross-scorer concordance throughout, and never human validation. The defensible claim is that the rubric is applied consistently by two independent passes under blinding. Cite the protocol: pipeline identity and citation evidence were withheld.

moderate

The answer keys were corrected after the pipelines were built

What the data shows. Twenty-four of 100 questions named a whole filing section rather than the supporting nodes. Those were re-derived to the minimal verified evidence set before the final run.

How to defend it. Argue it on mechanism, not on trust. The rule is mechanical, uniform, and was applied blind to every pipeline's output. The repair replays from the backup and reproduces the database exactly. Note that it was not common-mode. It inverted the vector against BM25 ordering on precision, which is why it could not stand.

moderate

Questions are not evenly spread across the filings

What the data shows. The most-sampled filing carries seventeen questions. The least carries one. Per-filing means rest on very different sample sizes.

How to defend it. Use the per-filing table as a spread check, never as a ranking, and say so where you present it. Every headline figure is paired within a question, so the imbalance cancels exactly.

moderate

The structural build cost is a floor, not a total

What the data shows. Eleven of thirteen filings recorded their token spend. Two did not, because the logging defect was fixed after those builds had run.

How to defend it. Report it as a measured floor over eleven filings, and name the two missing. The direction is safe: the true cost is higher, so the conclusion that this index is the most expensive to build is strengthened, not threatened.

moderate

A few questions are redundant or self-answering

What the data shows. Two pairs ask the same question of the same filing. A third pair splits one fact across two quadrants. Three questions restate most of their own answer. At most six of 100.

How to defend it. Disclose the count and argue common-mode. All three pipelines answer the same six, so the effect is a slight compression of the measured gap, not a shift in ordering. Removing them after retrieval behaviour was known would have been less defensible.

moderate

One quadrant tests a narrower skill than its definition implies

What the data shows. Six of the twenty-five implicit-table questions share two task shapes: counting signatories, and summing page numbers in an index.

How to defend it. Frame it as construct-coverage, not a validity defect in any row. Be specific about why the rows remain valid: counting signatories requires retrieving an intact tabular block, which is exactly the contrast being measured.

minor

The corpus carries parsing artefacts from the source filings

What the data shows. 1,089 nodes contain an unescaped HTML entity. Seven contain a raw tag. Four carry a corrupted digit run where a figure belongs. Exactly one question cites a corrupted node.

How to defend it. Argue common-mode, and for that one question, argue it is a feature. All three index the identical corpus. On that row the key records what the node actually says, so it rewards faithful extraction over a plausible figure recalled from training.

minor

The retrieval depths are 2, 3 and 5, not 3, 5 and 10

What the data shows. The sweep was narrowed on instruction after the design was written. Three depths are retained, so the 900-cell matrix is unchanged.

How to defend it. Record it as a scope decision with its consequence. The deepest setting is now 5, at or above the largest corrected evidence set, so full recall stays reachable. The token budget written against depth 10 becomes a conservative over-estimate.

What would weaken these findings

Stated plainly, so the claims can be scoped to match.

  1. A different question mix would move the vector against BM25 result. This is the most fragile finding here. They separate inside quadrants and cancel when pooled, so the mix does the work. State the mix whenever the null result is quoted.
  2. A thematic benchmark would move the structural result. Summary trees compress detail away. That is fatal for extraction and may help synthesis. Nothing here tests synthesis over a whole filing.
  3. A different answering model would move the leakage floor. A smaller model with less memorised knowledge would leak less, widening the measured gap.
  4. Nothing here would move by adding runs. The structural gaps span roughly two judge points, with intervals far wider than any plausible temperature-zero noise.
  5. Nothing here would move by adding depth inside this sweep. The ordering is identical at all three.

Reproducibility ledger

What can be reproduced, and from what.

  1. Every figure is computed at build time. No number is typed into a template. Re-running the generator reproduces the page.
  2. The statistics are seeded. Ten thousand bootstrap resamples from a fixed seed. Intervals reproduce exactly.
  3. Every judged row carries a rubric fingerprint. Recomputing reproduces the stored value in all four quadrants.
  4. Both answer-key corrections replay from the pre-repair backup and reproduce the current database row for row.
  5. Figures regenerate byte-identical. The citation repair is at its fixed point: re-running it performs zero further repairs.
  6. The corpus is frozen. 13 filings, 18,297 nodes, with a manifest in the repository.
  7. Every cell is accounted for. 900 benchmark cells and 60 gate rows, all scored, no nulls in any metric column.
  8. The record is deliberately selective. Thirty-eight deviations, fifteen bugs, four issues and two challenges, each logged with its reasoning.
  9. Those logs hold the consequential entries only. Minor fixes and small implementation refinements live in the commit history, not in the research record. Treat the counts above as a floor, not a total.

Closing

The reflex answer to document retrieval is embeddings. This study could not find evidence that the reflex is earned.

On 900 questions over thirteen annual reports, a statistical ranking function from 1994 matched a modern embedding stack with a cross-encoder reranker.

It built its index in under a second, against twenty-two minutes. It needed no model, no GPU and no training.

That is not an argument against vector search. The two separate inside quadrants, and each wins where you would expect.

It is an argument against skipping the baseline.

The structural paradigm lost, and lost expensively. But it lost for a reason the data can name: summaries discard the figures this benchmark asks for.

Ask different questions and that result may reverse. Nothing here tests that, and this document does not claim it.
