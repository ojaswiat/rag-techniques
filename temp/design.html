Which retrieval paradigm survives contact with a 10‑K?

A comparative benchmark of three RAG retrieval architectures — semantic, statistical, and structural — evaluated against SEC 10-K financial filings, to find which performs best on complex, structurally dense documents and where each one breaks down.

Phase 1 — Infrastructure Phase 2 — Ingestion (18 filings, 26,050 nodes) Phase 3–8 — Designed, not yet built
01 — Three Paradigms

Meaning, words, and structure

Every pipeline retrieves only within the one filing a query is about, shares the same answerer model, and is judged on the same rubric — so any score difference has to come from retrieval, not generation.

P1 — Vector

Semantic RAG

Retrieval by meaning

Dense embeddings plus a cross-encoder re-ranker. No metadata pre-filter — narrowing to a section at query time would risk leaking the answer.

bge‑small‑en‑v1.5
bge‑reranker‑base
ChromaDB · local CPU
P2 — BM25

Statistical RAG

Retrieval by exact words

Okapi BM25 over tokenised nodes. Purely statistical — never LlamaIndex's KeywordTableIndex, which calls an LLM and would collapse the contrast.

rank_bm25 · custom tokenizer
preserves numbers, %, currency
no LLM at any point
P3 — Structural

Summary‑Tree RAG

Retrieval by tree traversal

Hierarchical SummaryIndex over parent summaries. Expected to degrade on table-heavy queries — that predicted failure is a documented part of the study.

LlamaIndex SummaryIndex
one-time LLM build (8B)
local retrieval thereafter
Three further pipelines — P4 brute-force full-context, P5 naive vector, P6 hybrid fusion — are documented as reserved future scope. No modules exist for them.

The central loop

Runs 960 times — once per benchmark cell — and everything about crash-resumability hangs off its first and last step.

Scale, honestly

100 PQ × 3 pipelines × K ∈ {3,5,10} = 900 runs, plus a 60-output judge gate = 960 rows. Every cell runs once at temperature 0 — no repeated sampling.

04 — Evaluation Design

Four quadrants, three pillars

Every query set is stratified so each paradigm's strengths and failure modes surface by kind, not averaged away.

Q1 — Direct Text

Fact retrieval from dense prose. Exact Match applies.

Q3 — Direct Table

Strict cell / value extraction. Exact Match applies.

Q2 — Implicit Text

Multi-hop inference across pages. Judge-scored only.

Q4 — Implicit Table

Cross-row and footnote calculation. Judge-scored only.

Pillar 1 — Retrieval

Precision@K, Recall@K, Evidence Hit Rate — deterministic, code only, operating on node IDs.

Pillar 2 — Answer Quality

LLM judge 1–10 (primary), Token-F1 (secondary), Exact Match (Q1/Q3), Citation Audit (deterministic).

Coincidental-correctness trap: a model can answer correctly off the wrong node entirely. Token-F1 and Exact Match miss this; comparing cited node IDs against gt_citations is what catches it.

Binding invariants

Generator ≠ Critic family, and Answerer ≠ Judge family — so no model grades output from its own family.

The answerer is shared and identical across P1/P2/P3, so score differences must come from retrieval.

UNIQUE(source_set, query_id, pipeline, k_value) is the resume key — a crash never re-spends free-tier quota.
