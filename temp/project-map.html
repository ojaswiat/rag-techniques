What's actually inside project/?

This dissertation compares three ways of finding answers inside real company filings — searching by meaning, searching by keyword, and searching a summary tree — then scores which one answers best. Below is every piece of the codebase that exists so far, what it does in plain English, and exactly how far each phase has actually got.

The one rule that runs through everything: no AI grades its own homework

The AI that writes a question (Generator) is never the same model family as the AI that checks it (Critic). The AI that answers benchmark questions (Answerer) is never the same model family as the AI that later grades those answers (Judge). This "anti-self-grading" rule is enforced in the model-routing configuration everywhere it applies, not just hoped for.

Shared foundation built & in use

Four small files every other phase leans on. None of them are a "phase" of the dissertation themselves — they're the plumbing that makes every other phase safe, consistent, and cheap to run.

FOUNDATION
config.pyThe single source of truth for which AI model plays which role (Generator, Critic, Answerer, Judge, and the cheaper model used for the Phase 3 tree build), plus the project-wide "throttle" switch described below.
database_manager.pyThe only piece of code allowed to write raw database queries. Every other module goes through it instead of touching the database directly, so the five tables always stay in a consistent, predictable shape.
groq_client.pyA shared wrapper around every single AI call this project makes. If the free AI service says "slow down", it waits and retries automatically, and it caps how many calls can be in flight at once — so no phase can accidentally burn through the free quota in one burst.
loop_template.py — LOCAL_TEST_THROTTLEA tiny safety switch every long-running script copies. When it's on, a script processes only 3 items instead of the full batch, so brand-new code is always proven safe on a tiny sample before it's ever let loose on a real, quota-costing full run.
benchmark.dbThe single database file holding all five tables: nodes (the filing content), queries / golden_queries / judge_validation (the three question sets), and results (the eventual 900 graded benchmark answers). Every phase's real output ends up here.
tests/A full automated test suite, one file per module, that checks the code's logic works correctly without spending any real AI quota — fake model replies stand in for the real AI almost everywhere. A handful of separate, deliberately real "live smoke tests" exist purely to prove the real API behaves the way the fake ones assume.

Ingestion done

Turns 18 real SEC 10-K annual reports (6 companies, 3 fiscal years each) into small, labelled pieces of text and tables sitting in the database, ready for anything built later to search or summarise. This runs once per filing and is completely finished — verified directly against the live database: 26,050 nodes across all 18 filings, every one of the 6 companies represented.

Verified live: 26,050 nodes (23,733 text + 2,317 table) across AAPL, MSFT, TSLA, JPM, JNJ, WMT — all 3 years each.
INGESTION
fetch_filings.pyLooks up each company's real filing on the SEC's own public EDGAR lookup system and downloads the raw HTML. It never guesses a web address — it always asks SEC's own service for the real one.
LlamaParse (outside service)Not part of this project's own code — a third-party service that turns the raw, messy HTML into clean, readable Markdown, specifically instructed never to split a financial table apart while doing so.
node_builder.pyChops the clean Markdown into "nodes" — small, self-contained pieces, one per paragraph or one per whole table (a table is never split across two nodes). Also remembers which section of the filing each node fell under.
nodeThe smallest unit in the whole project — one paragraph, or one whole table. Every node has a unique node_id, remembers which filing it's from (document_id), whether it's "text" or "table" (node_type), and which section it sits under (parent_item_header).
node_idA unique label for one node, e.g. AAPL_2023_n0042 — the 42nd node found while processing Apple's 2023 filing.
document_idWhich filing a node belongs to, written as TICKER_YEAR, e.g. MSFT_2024.
node_typeEither "text" (ordinary prose) or "table" (a data table) — never anything else.
parent_item_headerWhich numbered section of the 10-K a node sits under, e.g. "Item 1A. Risk Factors" — lets later code group everything belonging to one topic together.
run_ingestion.pyThe conductor: runs fetch → parse → build-nodes → save-to-database for every filing on the list, skipping any filing already fully saved so a crash never re-downloads or re-pays for work already done.
parsing_audit.pyPulls a random sample of nodes so a human can eyeball whether parsing actually worked — tables intact, sections attributed correctly, nothing truncated. It can only present the evidence; only a human can confirm it looks right.

P3's summary-tree build partial — 9 / 18 filings

The "structural" pipeline (P3) won't search raw text — it searches a hierarchical summary of each filing, like a table of contents that gets more detailed the deeper you go. This one-time step builds that summary tree per filing using a cheap AI model, then saves the finished tree to disk so it's never rebuilt.

Verified live: storage/summary_index/ contains 9 finished trees — AAPL, MSFT, TSLA (all 3 years each). JPM, JNJ, WMT (9 filings) are blocked on Groq's free daily quota limit; the build stopped mid-run and hasn't been resumed. A possible swap to a different model for this step is under discussion, not yet decided.
P3 TREE BUILD
build_summary_index.pyReads all of one filing's nodes, hands them to llama-3.1-8b-instant (the cheapest model in the project's line-up), and asks it to write summaries at each level of a tree — several layers deep, each layer a summary of the layer below.
node_convert.pyA small translation step: reshapes this project's own node records into exactly the object shape a third-party library expects, so the tree-builder can hand nodes over without that library needing to know anything about this project's database.
summary treeA hierarchical structure — the whole filing is summarised at the top, branching down into section summaries, branching down into the original text. Phase 5's P3 pipeline will later search this tree top-down instead of scanning raw text, which is what makes it "structural" rather than "semantic" or "statistical".
storage/summary_index/Where each filing's finished tree is permanently saved, one folder per filing — so it only ever needs to be built once, no matter how many benchmark questions later get asked against it.
Groq daily quotaThe free AI-hosting tier's limit on how many tokens can be processed in a day. Hitting it mid-build for JPM/JNJ/WMT is exactly why 9 of the 18 trees aren't built yet — not a bug, a quota wall.

Dataset generation code built & fixed — 0 / 140 questions generated

The most recently worked-on part of the whole project. The goal: automatically write all 140 benchmark questions by having two different AI models check each other's work, so questions and their "correct" answers can be trusted without a human writing all 140 by hand. All of the code for this exists and has been through several rounds of bug-fixing very recently — but the real generation run hasn't happened yet.

Verified live: the queries, golden_queries and judge_validation tables all currently have zero rows — 0/25 in every quadrant, across all three question sets. The machinery is ready; nothing has been generated yet.

The three question sets — 140 questions total

140 QUESTIONS
PQ — Pipeline Queries (100)The real test. Every one of these gets asked to all three retrieval pipelines once the benchmark actually runs, and the three answers get compared against each other.
GQ — Golden Queries (20)A teaching set. For each one, the project owner personally writes a note explaining why a good answer is good, plus a 1–10 score. The Judge AI reads these every time it grades something, so it learns the human's standard first. Pipelines never see these.
JEQ — Judge Evaluation Queries (20)An exam for the Judge itself. Run through the pipelines once, scored by a human by hand and by the Judge blind, then compared — the Judge must agree with the human at least 80% of the time before it's trusted on the real 900 results.
Quadrant (Q1–Q4)Every question is tagged with one of four categories, evenly split within each set (25/5/5 per quadrant): Q1 a plain fact stated directly in text; Q2 something needing two or more passages connected; Q3 a specific number pulled straight from a table; Q4 a calculation or inference using a table.

How one question gets written and checked

GENERATE →
CHECK
Generator (gpt-oss-120b)Reads one section of a filing and proposes a candidate question, what it believes the correct answer is, and exactly which node_ids back that answer up.
Critic (Qwen3.6-27B)Given ONLY the question — never the Generator's answer — independently searches the same filing itself with its own small search tool and works out its own answer and citations. Deliberately a different AI model family, so it can't just agree with a familiar "voice".
search_tool.pyA tiny, dependency-free keyword search used only by the Critic to look through a filing's nodes for evidence — entirely separate from the real retrieval pipelines being benchmarked. It exists purely so the Critic can check itself.
cross_check.py — the 3-gate refereeA plain, code-only check — not another AI call — that only accepts a candidate if all three hold between the Generator's answer and the Critic's independent one: (1) their cited nodes overlap at least partly; (2) every number in the Generator's answer also appears in the Critic's answer; (3) the two answer texts are similar enough in meaning, measured with a fast, free, local text-similarity model. All three must pass, or the candidate is thrown away.
retry-with-feedbackEvery AI call runs at temperature 0 ("always answer the same way"), so blindly re-asking after a rejection would just fail the same way again. Instead the specific rejection reason is fed back to the Generator, which is told to pick a genuinely different fact from the same section — up to 3 attempts per section.
section_grouper.pyGathers all nodes sharing one section header (e.g. everything under "Item 7") into a single chunk, so the Generator sees a whole topic at once. About 6% of nodes have no header at all (cover pages, tables of contents, signatures) and are simply excluded.

Running the whole batch, fairly

ORCHESTRATOR
run_dataset_generation.pyThe conductor for this whole phase. Works out which (question-set, quadrant) slots are still short of target, feeds it sections in a fair rotation across all six companies, sends each section through Generator → Critic → cross-check, retries with feedback if rejected, and writes a running progress log throughout. Safe to stop and restart at any point — it re-checks the database on startup and never repeats already-finished work.
company-balanced routingSections are classified as mostly-prose (routed to Q1/Q2) or containing a table (routed to Q3/Q4), then handed out round-robin across all six companies — so, say, the table-question quadrants don't end up dominated by whichever company's filings happened to be processed first.
query_id numberingEach accepted question's ID number is worked out fresh from what's already saved in the database, not counted in-process — so if the run crashes and restarts, the next question picks up the correct next number instead of colliding with one already saved.
gq_label_export.py / gq_label_import.pyThe one deliberately manual step in this phase. Export writes the 20 golden queries to a plain text file with blank spaces for a human to fill in a score and explanation; import reads that filled-in file back into the database. The only place in the project where a human, not an AI, supplies grading ground truth.

What's been fixed this week, and what's still open

RECENT
WORK
Fixed — one bad reply no longer crashes the runA single malformed or unexpected AI response used to bring down the entire multi-hour batch. Now a per-attempt failure is logged and treated as a rejected attempt, and the run moves on.
Fixed — content-aware, company-balanced routingSections are now matched to the question type they can actually support (table content → table questions) and spread evenly across all 6 companies, instead of accidentally clustering by whichever filing came first.
Fixed — genuinely different retriesRetries now carry forward what specifically went wrong, so a second attempt is a real second attempt rather than a guaranteed repeat of the same rejected answer.
Fixed — fairer 3-way agreement checkThe check that used to reject correct answers over trivial wording or an extra unrelated number now uses three complementary, deliberately non-strict gates instead of one overly strict one.
Fixed — live progress visibilityThe run used to print nothing until the very end of a multi-hour session. It now prints a line per attempt, live, plus a durable log file.
Fixed — proven against the real APIA dedicated, opt-in live test now confirms the Critic's AI-to-AI "search, then answer" handshake genuinely works against the real service, not just against a faked stand-in.
Still open — oversized sectionsA few filing sections run unusually long. Handing an entire oversized section to the Generator or Critic in one go risks the AI call failing outright. A fix — splitting only the oversized sections into smaller pieces at safe boundaries, carefully never separating a table from the paragraph that explains it — has been discussed as a design, but is not yet built into the code.

Retrieval pipelines & Answerer not built yet

This is where the actual experiment happens: three different ways of finding relevant material in a filing, plus one shared "Answerer" AI that reads whatever each pipeline hands it and writes the actual answer. None of this exists as working code yet — only an empty pipelines/ folder skeleton and the Phase 3 tree-building code a future P3 pipeline will eventually read from.

Design note filed for later, not yet implemented: a retry-queue approach for the loop that will drive Phases 5 and 7, so a failed benchmark call can be revisited instead of silently skipped.
3 PIPELINES
+ ANSWERER
P1 — semantic vector searchFinds nodes whose meaning is closest to the question, using AI-generated embeddings and a local vector index. No cloud database — runs entirely on this machine.
P2 — statistical keyword searchFinds nodes with the most matching keywords, using the classic BM25 statistical ranking formula. Deliberately kept pure statistics with no AI involved in retrieval, so it stays a genuinely different contrast to P1 and P3.
P3 — structural searchSearches the hierarchical summary tree built back in Phase 3, top-down, using the tree's own structure to narrow in on the right section before finding the actual nodes.
Answerer (Llama 3.3 70B)The one AI model shared by all three pipelines at benchmark time. It never retrieves anything itself — it only reads whatever nodes its pipeline handed it and writes an answer, so any score difference reflects a difference in what got retrieved, not who's answering.
k_value (3, 5, 10)How many results each pipeline is allowed to retrieve for a given question. The benchmark tests all three settings, to see how each pipeline's performance changes with more or less room to work with.
6

Judge not built yet

A separate AI (same model family as the Critic, but deliberately never the same model as the Answerer it grades) that will read each pipeline's real answer next to the correct answer and score it. Before it's trusted on the real 900 results, it has to pass an exam first. None of this is built yet.

JUDGE
Judge (Qwen3.6-27B)Grades each pipeline's real answer against the known-correct answer, 1–10, once it exists and has passed its own exam below.
The 80% human-agreement gateThe pass/fail bar the Judge must clear before it's allowed anywhere near the real benchmark: score the same 20 JEQ × 3 pipelines = 60 outputs a human already scored by hand, and agree with that human at least 80% of the time. This check runs before the expensive full run, specifically so a badly-calibrated Judge can't quietly poison all 900 results.

Full benchmark run not built yet
